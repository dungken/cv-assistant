# 4.6 Tích hợp CV Health Dashboard end-to-end

Mục này trình bày quá trình tích hợp **CV Health Dashboard** — giao diện end-user trực quan hóa hai đóng góp khoa học của đề tài (Multi-criteria Freshness ở [mục 4.4](./4.4_multi_criteria_freshness.md) + Market Intel ở [mục 4.5](./4.5_market_intel.md)) trong một workflow thống nhất cho sinh viên.

## 4.6.1 Mục đích và workflow end-user

CV Health Dashboard trả lời 3 câu hỏi thực tế của sinh viên CNTT:

1. **"CV của em điểm bao nhiêu? Yếu chỗ nào?"** → Multi-criteria Freshness gauge 8 chiều.
2. **"Kỹ năng nào của em đang lên/xuống?"** → Skill Alerts trending up/down/new.
3. **"Em apply được JD nào trong tuần này?"** → Opportunity Window — 5 JD mới nhất phù hợp ≥ 70% với CV.

**Workflow chuẩn (Tối ưu Human-in-the-loop)**:

```
Sinh viên upload CV (PDF/DOCX)
    ↓
NER mBERT trích entity (SKILL, JOB_TITLE, DEGREE, ...)
    ↓
Hiển thị Bảng Review: Sinh viên xác nhận, xóa sai sót, hoặc thêm kỹ năng thủ công (Human-in-the-loop)
    ↓
POST /cv/me/confirm → lưu UserCVDB + trigger tính toán Freshness Score
    ↓
Dashboard fetch 4 widget song song (hoặc nhận qua WebSocket):
    - GET /health-score      → Gauge 8 chiều
    - GET /freshness/history → Time-series chart 8 tuần qua
    - GET /skill-alerts      → Trending up/down/new
    - GET /opportunity-window?days=7 → 5 JD mới matching
```

Round-trip end-to-end (từ click "Refresh" → 4 widget render xong): ~600–900 ms trên máy dev local (chi tiết bench ở 4.6.4).

## 4.6.2 Kiến trúc frontend

Frontend được implement bằng **React 19 + TypeScript + Tailwind CSS + Recharts**. Tổ chức theo feature folder [frontend/src/components/features/cv-health/](../../frontend/src/components/features/cv-health/):

**Bảng 4.12: Component và endpoint backend tương ứng**

| Component React | File | Endpoint backend | Render |
|---|---|---|---|
| **CVHealthDashboard** | `CVHealthDashboard.tsx` | Orchestrator | Layout 4 widget |
| **CVPicker** | `CVPicker.tsx` | `POST /cv/me` | Upload PDF/DOCX + select existing CV |
| **FreshnessGauge** | `FreshnessGauge.tsx` | `GET /health-score` | Radar chart 8 dimensions |

`CVHealthDashboard` quản lý state chung (`healthScore`, `history`, `alerts`, `opportunities`), gọi 4 endpoint **song song** (`Promise.all`) trong `fetchAll()` để giảm wall-clock.

```typescript
const [healthScore, setHealthScore] = useState<HealthScoreResponse | null>(null);
const [history, setHistory] = useState<FreshnessHistoryResponse | null>(null);
const [alerts, setAlerts] = useState<SkillAlertsResponse | null>(null);
const [opportunities, setOpportunities] = useState<OpportunityWindowResponse | null>(null);

const fetchAll = useCallback(async () => {
    await Promise.all([
        fetchHealthScore(userId),
        fetchHistory(userId),
        fetchAlerts(userId),
        fetchOpportunities(userId, days=7),
    ]);
}, [userId]);
```

## 4.6.3 BackgroundTask recompute Freshness

Một thách thức UX: nếu user upload CV mới rồi load dashboard ngay → engine chưa kịp compute → dashboard rỗng. Đề tài giải bằng **FastAPI BackgroundTask** triggered từ `POST /cv/me`:

```python
@app.post("/cv/me", response_model=CVUpsertResponse)
def upsert_cv(request, background_tasks: BackgroundTasks, db):
    cv_store.upsert_cv(db, request.user_id, request.target_role, request.skills, ...)
    background_tasks.add_task(_recompute_freshness_bg, request.user_id)
    return CVUpsertResponse(..., recompute_scheduled=True)
```

`_recompute_freshness_bg(user_id)` chạy **async sau khi response trả về**:

```python
def _recompute_freshness_bg(user_id: str) -> None:
    db = SessionLocal()  # session riêng (request session đã đóng)
    try:
        cv = cv_store.get_cv(db, user_id)
        engine = get_freshness_engine()
        result = engine.compute(db, cv_skills, role=cv.target_role)
        record_history_and_alert(db, user_id, result)
    finally:
        db.close()
```

Hàm `record_history_and_alert` (xem [freshness_engine.py:313](../../services/skill_service/services/freshness_engine.py#L313)) làm 2 việc atomically: (i) insert row mới vào `skill_freshness_history`, (ii) so sánh với snapshot trước cùng (user, role) — nếu drop > 5 điểm thì insert vào `skill_freshness_alerts`.

**Lý do background**: compute Freshness 8 chiều mất ~1.5s (load ontology + query skill_trends + tính 8 dim). Nếu chạy sync trong endpoint upload CV thì user phải chờ → tệ UX. Background pattern cho phép `POST /cv/me` trả ngay `{recompute_scheduled: true}` rồi dashboard tự fetch khi user load → tổng UX wait < 3s.

## 4.6.4 Hiệu năng end-to-end

Đo wall-clock cho 1 user có CV size trung bình (10 skill, 3 project, 2 experience block) trên máy dev local:

**Bảng 4.13: Latency end-to-end từng giai đoạn**

| Giai đoạn | Latency | Note |
|---|---|---|
| `POST /cv/me` (upsert) | ~80 ms | Sync — chỉ insert DB |
| BackgroundTask recompute Freshness | ~1.500 ms | Async — không block user |
| `GET /health-score` | ~120 ms | Đã có cache trong RAM của engine sau lần compute đầu |
| `GET /freshness/history` | ~30 ms | Query đơn giản trên `skill_freshness_history` |
| `GET /skill-alerts` | ~50 ms | Query `skill_freshness_alerts` |
| `GET /opportunity-window?days=7` | ~250 ms | Tính ATS score cho ~150 JD active 7 ngày |
| **Tổng 4 widget song song** | **~600–900 ms** | Bottleneck: opportunity-window |

→ Đáp ứng yêu cầu phi chức năng *"CV Health Dashboard load lần đầu ≤ 3 giây"* ([§3.1.2](../chuong3/3.1_phan_tich_yeu_cau.md)).

## 4.6.5 UI/UX highlights

### Radar chart 8 chiều thay vì single gauge

Đây là **lựa chọn thiết kế quan trọng**: hầu hết ATS tool hiện có hiển thị 1 số (overall score 75/100) — không cho user biết yếu chỗ nào. Radar chart 8 chiều buộc UI phải show từng dimension riêng → user nhìn thấy ngay *"điểm Achievement = 30 đang kéo tổng xuống, cần thêm cert"*.

### Chế độ Giả lập Tương lai (What-if Simulation)

Tính năng tương tác cốt lõi tạo cảm giác "WOW": Người dùng có thể bật chế độ Simulation, kéo thả các kỹ năng hot (lấy từ dữ liệu Market Intel) vào hồ sơ giả định của mình. Khi đó, Radar Chart và bảng Opportunity Window sẽ lập tức cập nhật để hiển thị: *"Nếu bạn học thêm Docker, điểm Freshness sẽ tăng từ 65 lên 80, và bạn sẽ mở khóa thêm 15 cơ hội việc làm mới"*. Đây là bước chuyển từ việc **đánh giá bị động** sang **huấn luyện chủ động**.

```
        Skill (80)
           ★
    ★              ★
Market(70)      Experience(85)
  ★                  ★
Completeness(100)  Project(90)
  ★                  ★
Language(80)    Education(95)
       ★      ★
     Achievement (30)  ← user thấy gap rõ
```

### Empty states có hướng dẫn

| Trạng thái | UI behavior |
|---|---|
| Chưa upload CV | Wizard "Upload CV để bắt đầu" thay vì dashboard rỗng |
| CV mới upload, BG chưa xong | Spinner + "Đang tính Freshness Score, ~3s" |
| < 4 tuần market data | "Đang thu thập trend, quay lại sau X ngày" |
| Không có JD phù hợp tuần này | "Thử mở rộng role mục tiêu hoặc location" |

### Responsive

Dashboard hoạt động trên desktop (≥ 1024px: 3 cột top section), tablet (768–1023px: 2 cột), mobile (< 768px: stack vertical, FreshnessGauge thu nhỏ). Dùng TailwindCSS breakpoints — không thêm CSS custom.

## 4.6.6 Tích hợp với Market Intel Dashboard

CV Health Dashboard không phải dashboard duy nhất — đề tài có **2 dashboard song song**:

| Dashboard | Đối tượng | Cá nhân hóa? |
|---|---|---|
| **CV Health** | User cá nhân, đã upload CV | ✅ Per-user state |
| **Market Intel** | Mọi visitor | ❌ Aggregate macro view |

Hai dashboard **chia sẻ chung pool dữ liệu** (1.604 JD + skill ontology 460 entries) và đặt cạnh nhau trong app với nav switch. User flow tự nhiên:

1. Lần đầu → mở **Market Intel** xem "role nào hot, lương bao nhiêu, skill gì cần".
2. Quyết định role mục tiêu → upload CV → chuyển sang **CV Health** xem điểm + cần cải thiện gì.
3. Cải thiện CV → upload lại → so sánh Freshness theo time-series.

## 4.6.7 Hạn chế thừa nhận

**H1 — Authentication chưa hoàn thiện**: hiện dùng `user_id` truyền trực tiếp qua URL/query param thay vì JWT từ Gateway. Trong scope DATN ưu tiên backend logic, chưa wire full OAuth flow. Hướng phát triển: tích hợp Gateway JWT đầy đủ + login flow.

**H2 — Frontend test thủ công**: không có Jest/Playwright test cho component. Test chỉ chạy thủ công qua browser. Trong scope 18 tuần với nhân lực 1 sinh viên, ưu tiên test backend (pytest) — phía nơi rủi ro chính nằm ở logic algorithm.

**H3 — Mobile UX chưa polished**: layout responsive cơ bản nhưng radar chart 8 chiều khó đọc trên màn hình < 400px. Hướng phát triển: thay radar bằng bar chart vertical cho mobile.

**H4 — Email digest chưa active**: API Gateway có scaffold `EmailService.cs` để gửi digest weekly, nhưng chưa wire vào cron trong scope DATN do mất công setup SMTP + GDPR cho email cá nhân sinh viên.
